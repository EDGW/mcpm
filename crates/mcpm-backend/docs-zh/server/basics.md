# 基础

基础操作处理服务端的身份：一个目录是哪个 Minecraft 版本、哪个 Loader 的服务端，这个事实如何记录下来，
以及初始化时一并写入的启动配置。执行位置与失败的共同规则见 [README](README.md)。

服务端身份由名称、Minecraft 版本、Loader 及其版本组成，记录在服务端目录的登记文件里。`launch.toml`
保存启动配置，`conf.toml` 保存用户设置。

## 操作

| Operation | 作用 |
| --- | --- |
| `server.info` | 读取服务端的登记信息 |
| `server.init.recognize` | 从启动脚本推断服务端身份，给出候选，不写入任何内容 |
| `server.init` | 把选定的身份写入服务端目录，并按需发布启动配置 |
| `server.init.prepare_remote` | 建立指向远端服务端的 Remote workspace 之前，先在远端做好准备 |

识别与初始化是两个独立的步骤：先识别得到候选，用户选定其中一个，再用选定的结果初始化。

## `server.info`

返回服务端的名称、路径、Minecraft 版本、Loader 及版本、启动命令，以及 `launch.toml`、`conf.toml`
是否存在。这两个配置文件只确认是否存在，不读取内容，因此结果不代表启动一定能成功。登记缺失或损坏时报错，
因为没有身份可报告。

## `server.init.recognize`

读取启动脚本，推断它启动的是什么服务端。它只读取脚本文本和相关文件，不会运行脚本、Java 或安装器。
已有登记损坏也不影响识别；识别不写文件，不创建 Git 仓库，也不改动现有配置。

每个候选包含推断出的身份、依据所在的脚本行、主类，以及初始化时将发布的配置草稿。调用方可以传入
Minecraft 版本或 Loader 来筛选候选，这些值只用来过滤，不会补出脚本里没有的信息。

候选列表返回给调用方，由调用方在本机选择。选定后，调用方把所选候选的内容交给 `server.init`，识别阶段
不保留任何状态。

## `server.init`

把一个身份写入服务端目录。这个身份可以是识别得到的候选，也可以是用户手动给出的完整信息。

- 调用方要求发布配置时，写入身份、`launch.toml` 和 `conf.toml`；否则只登记身份。
- 识别得到的候选带有配置草稿，`launch.toml` 由它生成。手动给出的身份没有草稿，因此不生成
  `launch.toml`。
- 目录已有登记时，必须指定 `force` 才会替换。`conf.toml` 默认保留已有内容，只有同时要求替换时才会
  重新生成，而这个要求必须与 `force` 一起给出。
- 工作区标记在上述内容发布成功之后才写入。

初始化时还会准备 Git 仓库：

| 选项 | 行为 |
| --- | --- |
| 默认 | 目录本身、上级目录或 worktree 中已有仓库就复用，都没有时才在服务端目录创建 |
| `git` | 要求服务端目录自身有仓库 |
| `no_git` | 不检查，也不创建 |

两个选项不能同时使用。文件不会被自动暂存或提交。仓库损坏或 Git 命令失败时报错。

初始化过程依次报告校验和写入两个阶段，最后返回写入结果。发布、工作区标记或传输中途失败时，已写入的
文件保留，重试之前应先检查服务端目录的实际内容。

## `server.init.prepare_remote`

建立 Remote workspace 需要两步：先在远端服务端上做准备，再在本机写入指向它的登记。这个操作负责第一步，
在远端主机上运行：确认目标是一个 Local Server，并按要求准备 Git 仓库。

它不发布服务端配置。第二步由 `workspace.register_remote` 在本机完成；本操作不修改本机登记，也不会在
本机创建 Git 仓库。
