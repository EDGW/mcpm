## `mcpm init`

Register a Local Server, or with `--remote`, initialize server R on the SSH host and register a Remote workspace placeholder P on the caller. P stores only connection registration; all server business data remains on R.

```sh
# Recognize and register a server on this machine
mcpm init ./server
mcpm init ./server --start-script run.bat

# Register directly using complete metadata
mcpm init ./server --minecraft-version 1.20.1 --loader forge --loader-version 47.3.12
mcpm init ./server --minecraft-version 1.21.1 --loader vanilla

# Skip Git detection and initialization
mcpm init ./server --minecraft-version 1.21.1 --loader vanilla --no-git

# Create a repository in server even when a parent repository exists
mcpm init ./server --force --minecraft-version 1.21.1 --loader vanilla --git

# Initialize a Local Server on the SSH host; the positional path is remote
mcpm --ssh 'ssh user@host' init /srv/minecraft --minecraft-version 1.21.1 --loader vanilla

# Initialize host R and register caller placeholder P
mcpm --ssh 'ssh user@windows' --ssh-mcpm 'C:\mcpm-tools.exe' init ./workspace --remote 'D:\EDGW-26Summer' --start-script run.bat

# Subsequent commands use the saved connection automatically
mcpm info ./workspace
mcpm mods list --server ./workspace
```

## Arguments

- `[PATH]`: An existing directory, default `.`. With `--remote`, this is caller placeholder P; the `REMOTE_PATH` is host server R.
- `--remote <REMOTE_PATH>`: Recognize and register R on the SSH host, then register P locally. `REMOTE_PATH` is interpreted by the host platform.
- `--start-script <FILE>` and metadata filters: Passed to host recognition; allowed with `--remote`. Complete metadata registers directly on R; incomplete filters recognize on R and select candidates on the caller.
- `--force`: Controls only host R server registration/config replacement.
- `--replace`: Controls only caller P Remote registration replacement; valid only with `--remote`.
- `--foverride-conf`: Regenerates host R `conf.toml`, still requires `--force`, and may be combined with `--remote`.
- `--git` / `--no-git`: Apply only to host R; caller P never performs Git setup.
- `--no-ui`: Disable candidate selection TUI; multiple host candidates require more specific filters.
- `--full-command`: Show the complete startup command when an older snapshot is available.
- `--no-ui`: Disable candidate selection TUI and use Console mode. Multiple candidates require more specific recognition filters. Combined with global `--raw`, uses Raw mode.
- `--full-command`: Show the complete startup command in the result. Console output normally fits one line with `(+N)` for omitted characters; Raw output always retains the complete command.

SSH connection settings and the remote mcpm executable use the existing [global options](../README.md#global-options), rather than separate `server init` arguments.

## Behavior

### Local behavior

Without explicit global SSH options, a Local or unregistered `PATH` initializes on this machine. Successful initialization produces:

```text
conf.toml      # Java, memory, GC and user settings
launch.toml    # Generated by script import, omitted for manual registration
.mcpm/
├── .gitignore   # Ignores /cache, /data and /registration.lock
├── mcpm.json    # version: 1, type: local
└── server.json  # Local identity metadata, version: 3
```

Initializing a Local or Remote workspace creates `.mcpm/.gitignore` containing `# Added by mcpm`, a blank line, and the `/cache`, `/data`, `/registration.lock`, `/launch.lock`, and `/launch-publication.json` rules. No stash ignore rule is added. Existing contents are preserved. If the file already ends with the complete block when blank lines are ignored, nothing is appended; otherwise, the complete block is appended after a newline. Repeated initialization with `--force` therefore does not duplicate the block.

Default Git behavior:

- Before writing registration, use Git to discover whether the target already belongs to a repository. Existing repositories, parent repositories, and worktrees are reused.
- When no repository is found, run `git init` in the target directory. Files are not automatically staged or committed.
- Git must be installed on the host performing initialization. An unavailable Git executable, damaged repository, or failed initialization produces an error. Use `--no-git` to skip Git operations.
- Recognition alone or cancelling candidate selection does not initialize Git.
- `--force` also performs Git setup; `--git` requires the target's own repository and `--no-git` skips setup.
- Console mode shows a white one-line notification before the server information, followed by a blank line, reporting whether the repository was created or initialization was skipped because one already exists, along with the target path. SSH results are displayed locally. Every successful initialization ends with a green `Initialized successfully.` after the server information, including when using `--no-git`. Raw output retains its existing server information fields; `--no-git` produces no Git message. `NO_COLOR` disables colors.

mcpm owns `mcpm.json`, which selects the workspace type. mcpm-backend parses and persists Local `server.json`. Legacy directories without `mcpm.json` are Local. Local metadata versions 1 and 2 remain readable; reading never rewrites them, and explicit reinitialization writes identity-only version 3.

Complete `--minecraft-version` and `--loader` arguments, plus `--loader-version` unless vanilla, initialize directly without reading scripts. Otherwise recognition uses `run.bat` on Windows or `run.sh` on Unix and filters verified candidates against the supplied fields.

Recognition reads scripts and identity evidence without running scripts, Java, installers, or downloads. Common Forge/NeoForge layouts, Forge shims, Fabric installations, and vanilla JARs with version metadata are supported. Static recognition handles literal assignments, quoting, continuations, directory changes, script references, and Java argument files. Dynamic conditions, loops, pipes, unresolved variables, and recursive references may prevent recognition. Successful recognition does not guarantee launchability; supply complete manual metadata when recognition is unavailable.

A unique candidate registers immediately. Multiple candidates open the TUI: Up/Down selects, Enter confirms, and Esc/Ctrl-C cancels. Selection requires local terminal stdout/stderr without `--raw` or `--no-ui`. Console and Raw require an unambiguous candidate; redirected stdout automatically selects Raw.

Local imports publish complete configuration for the selected candidate:

- Imported Java, memory, GC and server settings are enabled in `conf.toml`; unspecified settings remain commented out.
- Fixed arguments, entry, actual working directory and explicit environment overrides belong to `launch.toml`. Class, JAR and module entries retain their entry kind; source entries and uncertain option boundaries are rejected.
- Java argument files are flattened during static import. Source changes require an explicit reimport.
- Every imported `-javaagent` must refer to an existing readable file, resolved against the original Java working directory. Missing agents fail import without downloading.
- The JAR manifest's `Premain-Class` identifies authlib-injector, including renamed files. Its agent and representable properties move into `[authlib-injector]` in `conf.toml`. The imported `jar` remains a manual path: no copying, download or managed metadata. Foreign agents and unknown or unrepresentable properties retain their raw arguments; multiple authlib-injector agents are ambiguous and fail.
- Existing `conf.toml` is preserved on first registration and on `--force`; replacing it additionally requires `--foverride-conf`. Invalid preserved settings or conflicts block publication.
- Backend publication uses a recovery journal. An interrupted import must be recovered through explicit initialization before launch.
- Workspace type marking remains a separate frontend step. Its failure reports server files already committed.
- Results show [`server info`](info.md) and file changes; inspect configuration files for individual settings. Use [`launch`](launch.md) to start the server.

### Remote behavior

With `--remote`, P is the caller-side Remote workspace placeholder and R is the server directory on the SSH host. P stores only SSH, executable, and host-path registration. Recognition, `server.json`, `conf.toml`, `launch.toml`, configuration publication, and Git detection/initialization all run on host R.

```text
mcpm --ssh COMMAND [--ssh-mcpm EXE] init P --remote R [recognition options] [--force] [--replace]
```

Complete manual metadata registers directly on R. Otherwise recognition runs on R and candidate selection runs on the caller. An empty `--start-script` lets the host select its platform default; the caller platform is never used.

`--force` replaces only host registration/configuration; `--replace` replaces only P's Remote registration. `--git` and `--no-git` apply only to R. P's codec is `.mcpm/remote_info.json`; `.mcpm/server.json` remains Local server metadata only.

If host initialization succeeds but P registration fails, host files are not rolled back. The command reports that R completed while P remains unregistered and suggests retrying registration with `--replace` or using the existing workspace registration capability manually.
