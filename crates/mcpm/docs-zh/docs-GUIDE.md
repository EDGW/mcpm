# 文档编写指南

如果你使用AI编写文档，你应该遵守这份指南。

适用于 `crates/mcpm/docs-zh` 下的命令文档和 CLI 帮助文案。格式以 `server/basics.md` 为基准。

## 读者视角

- 文档面向使用者，首先说明命令做什么、何时使用、会得到什么结果。
- 从使用流程组织内容，在迁移的时候避免直接搬运旧文档或按实现结构分段。
- 读者不需要了解内部设计即可完成操作。

## 结构

每个命令按以下顺序组织：

1. 用途和适用场景
2. 命令形式
3. 选项
4. 示例
5. 该命令独有的行为细节
6. 与其他命令共用的行为

## 分节层级

- 命令独有的章节放在该命令下面。例如 `launch` 的临时覆盖、配置文件、认证，应作为 `mcpm launch` 的子章节。
- 多个命令共用的章节放在文档末尾，例如输出模式、命令输入、日志、状态。
- 避免同一信息出现在多个章节；确需引用时使用链接。

## 内容取舍

保留：

- 命令用途、参数、选项、默认值
- 用户可见的输出、状态、提示和错误
- 操作步骤、限制和结果
- 配置文件结构、路径解析和认证行为
- 可能会引起误会的行为，比如说看起来可能会执行某个操作的某个命令实际上不执行某个操作

删除：

- 显而易见的对比，例如“两个命令不同”
- 重复描述和可由选项表直接看出的信息
- 实现细节：内部状态机、锁、超时、缓存、元数据、传输过程、内部术语
- 开发过程中讨论的问题和与使用无关的约束
- 无需解释的行为，比如说 remove 并不添加项目

## 语言

- 使用正式书面语，避免口语化表达。
- 直接陈述行为：命令做什么、界面显示什么、失败时发生什么。
- 避免连续否定句式，例如“不 A，不 B，也不 C”。优先使用肯定陈述，或将限制拆成独立句子。
- 一个段落只表达一个主题。

## 输出模式

- Console、Raw、TUI 等模式按行为描述，不按内部绘制或传输方式描述。
- 只在用户需要理解输出差异时说明 stdout、stderr 和颜色行为。

## CLI 帮助文案

- 按逻辑分段，标题使用 **bold + underline**。
- 引用的 CLI 参数使用 **bold**。
- 正文保持默认样式。
- 删除 `Primary`、frame、session、shim、frontend 等内部术语。
- 按用户阅读顺序整合内容，不在短段落中堆叠限制。

## 中英文同步

- 中文文档完成后同步英文版本，保持章节结构一致。
- 迁移完成后删除对应的 legacy 文档，并更新各级索引。
